# Agent-facing CLI P1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make bb-workflow observable, cancellable, and reliably operable by calling agents without breaking its CLI or acceptance guarantees.

**Architecture:** Extend the current CLI and workflow; no new service or provider SDK.
Live progress is advisory and separate from authoritative audit state. Machine
output is an opt-in envelope around existing command payloads.

**Tech Stack:** Python 3.11+ stdlib, unittest fixtures, Ruff/reviewdog.

**Spec:** docs/superpowers/specs/2026-10-25-agent-cli-p1.md

## Global Constraints

- Python 3.11+, runtime stdlib only; no paid provider sessions.
- Keep stage order, both independent reviews, frozen-source checks, strict response
  validation, full audit evidence, and explicit apply. Never change models silently.
- Retain unknown usage as unknown. Heartbeat proves supervisor activity only.
- Preserve default CLI output and existing 0/1/2/130 exit semantics; additive progress
  metadata and the initial stderr announcement are compatible extensions.
- Do not implement resume, automatic stale-lock removal, provider retry redesign,
  apply preview, Codex MCP, or an SDK migration in this change.
- SIGKILL/crashes remain outside graceful cleanup guarantees. Do not claim a stale
  heartbeat proves process death or authorizes deletion of the lock.

## Review Focus

- Repeated SIGTERM during cleanup must not interrupt rollback, log persistence or
  lock release. Signal handlers must be restored when embedded main() returns.
- CLI mode flags after a subcommand, malformed arguments, --help and literal task
  text after -- must not bypass the machine contract or change legacy behavior.
- A malformed/stale progress sidecar or heartbeat failure cannot imply success or
  overwrite authoritative state; terminal status ignores stale live telemetry.
- Check metadata probes, blocking provider fixtures and failed report writes must
  preserve cancellation evidence and must not grant apply eligibility.
- Operator installation must work outside the orchestrator repository and avoid
  symlinks or automatically granting the backend authority to launch nested runs.

### Task 1: Observable runs and controlled cancellation

**Files:** Create src/bb_workflow/lifecycle.py and tests/test_lifecycle.py.
Modify src/bb_workflow/cli.py, engine.py, verification.py as needed; process.py only
if required for safe cancellation. Extend tests/test_cli.py, test_engine.py,
test_process.py/test_workspace.py where relevant. Update docs/architecture.md.

**Interfaces:**
- Keep Workflow's existing injected invoke_fn/process_fn/progress contracts.
- Add optional Workflow event callback for structured start/phase/finish events.
- execute_checks may gain optional on_start callback receiving PlannedCheck;
  do not add new required kwargs to injected provider/process callables.
- run --events-jsonl emits versioned JSONL lifecycle events to stderr, with run_dir,
  event and phase. Default mode still emits text progress and final JSON stdout.
- status --summary may add nested progress read from progress.json only while state
  is running. Full status still returns the stored state unchanged.

- [ ] Write regression tests before implementation: observe run directory before a
  blocking fixture finishes; read active check/role while it is blocked; see a
  heartbeat advance without checkpoint/token changes; final state ignores stale or
  malformed telemetry. Preserve the existing legacy-summary test.
- [ ] Run focused tests and record expected failures.
- [ ] Implement a context-managed advisory progress tracker with atomic sidecar
  writes, a five-second heartbeat and a bounded thread shutdown. It owns its own
  immutable/copy-on-update metadata; it never mutates state.json from its worker.
  Expose version, run_dir, pid, phase, active_operation, updated_at, elapsed_seconds
  and heartbeat_interval_seconds. Active operation identifies role, or check id,
  variant and command. Tests may use a shorter interval on the tracker itself.
  Handle sidecar failure explicitly without unhandled thread errors or success
  claims. Start after initial state persistence and close before run exits.
- [ ] Implement scoped POSIX main-thread SIGTERM handling around CLI execution:

  must retain their current responsibility. Windows uses existing Ctrl+C cleanup.
- [ ] Add real subprocess fixture tests for SIGTERM during a long run and verify:
  exit 130, interrupted state/report, logs retained, child terminated, lock released.
  Test signal handler restoration and repeated termination during cleanup. Test
  apply cancellation using existing rollback fixtures without weakening guarantees.
- [ ] Run focused tests then full unittest suite; Ruff with raw reviewdog output

### Task 2: Opt-in versioned machine CLI

**Files:** Modify src/bb_workflow/cli.py; create src/bb_workflow/cli_output.py if it
keeps serialization separate. Extend errors in engine.py/workspace.py and related
modules only where structured causes are required. Tests/test_cli.py and appropriate
engine/workspace regression tests. Create docs/cli-contract.md.

**Interfaces:**
- --json is accepted before or after the command (except after literal --).
- Envelope version 1: schema_version, command, ok, exit_code, data, error.
  data is the existing command payload (or null when no payload is available).
  error is null on command success; otherwise contains code, message, retryable,
  next_action (a stable action identifier), and artifacts (known file paths only).
- ok means command success, not workflow approval: status on a failed run can have
  ok=true and data.status=failed; plan with requirements_needed=true stays exit 0.
- --json --help (also subcommand help) returns an envelope containing help text;
  legacy help and parse errors retain argparse/SystemExit behavior.
- Error codes are semantic, not derived by matching prose. Cover invalid_arguments,
  invalid_config, invalid_requirements, requirements_required, project_locked,
  source_conflict, candidate_conflict, provider_error, interrupted, io_error,
  invalid_state, workspace_error and terminal workflow statuses. Generic fallback
  remains explicit; do not promise every provider subtype is classified.
- retryable describes safe automatic repetition of the CLI command, not the
  backend's per-role retry policy. Default false for failed/partial runs and apply.
  next_action guides inspection/correction and never automatically executes apply,
  deletes locks, logs in, or restarts a paid run.
- Task 1 structured progress stays on stderr and does not contaminate stdout.

- [ ] Write failing contract tests for each command's envelope and default-output
  compatibility, parser errors, help, mode placement, missing configuration,
  missing requirements, lock conflict, failed run, interrupted run, status read,
  malformed state and apply source/candidate conflicts.
- [ ] Run focused tests and record expected failures.
- [ ] Refactor CLI result emission minimally; avoid capturing/reparsing printed
  stdout. Add typed error metadata at its origin and persist meaningful workflow
  failure categories so CLI need not parse reason strings. Keep public exception
  constructors compatible and preserve legacy run/status/verify payloads.
- [ ] Document envelope, error taxonomy, exit/status distinctions, progress channel,
  artifact links, unknown usage and compatibility policy in docs/cli-contract.md.
- [ ] Run focused tests, full unittest suite and Ruff/format checks; commit task.
